# Aftercare web

The web build is **not** a second app: `/app/` is the same Dart code (glossary,
paths, community feed, profiles, settings) compiled for the browser, so a fix or
a feature lands on the phone and the web at the same time. `/` is a hand-written
marketing page for the Aftercare brand that introduces the app and links into it.
The Flutter app itself still ships as “Kinktionary” (Android label, manifest,
window title); only the marketing page carries the Aftercare name so far.

```
landing/        Aftercare marketing page: index.html, styles.css, main.js, assets/
web/            Flutter browser shell: index.html, manifest.json, icons, favicon
lib/            the app itself — shared with Android and iOS
tools/build_site.sh   builds landing/ + the app into build/site
build/site/     the deployable site (generated, git-ignored)
```

Landing assets: `aftercare.png` (logo, supplied at 64×64 — replace it with a
larger or vector version when one exists), `safety.png` and `term.png` (real app
screenshots), `privacy.svg` (illustration). Images rely on `height: auto`, so
keep new screenshots at their true aspect ratio.

## Run locally

```sh
flutter run -d chrome                      # the app alone, debug + hot reload
flutter run -d web-server --web-port 8080  # the app alone, no browser window
```

For the whole site (landing page plus app under `/app/`):

```sh
./tools/build_site.sh
python3 -m http.server 8137 --directory build/site
```

Rebuild after changing `landing/` — the script copies it in. Rebuilding deletes
`build/site`, so stop and restart any server whose working directory is there.

## Wide-screen layout

From 860px wide the tabs move from the bottom bar to a rail pinned to the left
edge of the window, and the wallpaper runs behind everything. The reading column
(620px) is centred on the window with the sidebar (320px) to its right, so it
sits where a desktop feed does rather than stretched edge to edge.

The rail is icon-only until the mouse enters it, then opens to 208px and names
every section. It opens only when there is empty space beside the column to grow
into (roughly 1100px and wider); below that it stays collapsed rather than cover
the feed. The sidebar appears whenever the column plus sidebar still fit in the
window.

Routes pushed on top of the shell (a term, settings, the composer) are capped at
760px by `PatternScaffold` in `lib/widgets/pattern_background.dart`, which the
shell opts out of with `constrainWidth: false`. Breakpoints live in
`lib/screens/home_shell.dart`.

## App Check on the web

This Firebase project enforces App Check on Auth and Firestore. A web build with
no App Check token cannot sign in — the request comes back
`401 Firebase App Check token is invalid`.

`tools/build_site.sh` therefore builds with the web app's registered **debug**
token (`--dart-define=APP_CHECK_DEBUG=true` plus the token). That is a
development crutch: it only proves the app is the app, it is not a production
credential, and it is registered per Firebase web app (`App Check → Apps → the
web app → Manage debug tokens`). Delete it there before the site is public.

For a real deployment, register reCAPTCHA v3 for the web app in the Firebase
console and build with the site key instead:

```sh
APP_CHECK_RECAPTCHA_SITE_KEY=<site-key> ./tools/build_site.sh --recaptcha
```

A debug build without a token prints one in the browser console; register that
value if you prefer not to bake a token into the build.

## Firebase

The web app is registered in your Firebase project; its config lives in
`lib/firebase_options.dart` (`DefaultFirebaseOptions.web`), generated by
`flutterfire configure`.

Same Firebase services as the app: Authentication (email/password), Firestore
for posts, replies, likes, profiles and friend edges, and Cloud Storage for
avatars. Signed-in state persists across visits.

**Authorised domains.** `localhost` is allowed by default. Before going live,
add the production hostname in **Firebase console → Authentication → Settings →
Authorized domains**, or sign-in fails with `auth/unauthorized-domain`.

**App Check.** See “App Check on the web” above: the site currently builds with
a registered debug token, and production needs reCAPTCHA v3 for the web app.

**Storage CORS.** Browser uploads of profile photos need CORS on the bucket:

```sh
gcloud storage buckets update gs://<your-project-id>.firebasestorage.app \
  --cors-file=cors.json
```

with `cors.json` allowing `GET, POST, PUT` from your site origin.

## Local state

Bookmarks, notes, path progress and the age gate use `shared_preferences`,
which maps to `localStorage` on the web. They are per-browser: a phone and a
browser keep separate private notes, exactly as two phones would.

## Known gaps

- PWA icons are still Flutter's defaults; replace `icons/Icon-*.png` and
  `favicon.png` with the Aftercare art (512×512 for install prompts). The
  landing page already uses `landing/assets/aftercare.png`.
- The supplied logo is only 64×64, so it is soft on high-density screens; it
  wants a 512px or SVG original.
- The app is still named Kinktionary; only the marketing page says Aftercare.
- The landing page has no analytics by design, so there is nothing measuring
  whether the “Open the app” button gets used.
- The site is only served locally so far; hosting and the Authorized-domain
  entry are still to do.
